# softcopy-materials 软著材料生成技能 · 介绍文档

## 一、技能概述

**softcopy-materials** 是一个本地运行的 coding agent skill，用于从**真实项目源码**出发，生成中国软件著作权登记所需的全部申请资料：申请表信息、程序鉴别材料（源代码文档）、以及操作手册或技术方案文档，最终经 OfficeCLI 输出为可直接提交前导出 PDF 的正式 Word/TXT 文件。

- **触发方式**：用户提到 软件著作权、软著、软著申请、操作手册、技术方案文档、申请表信息 等关键词，或要求为软著登记准备 Word/TXT 材料时。
- **适用宿主**：任何支持本地 skill 目录的 coding agent（zcode、workbuddy、mimo、trae、qorder、opencode、pi、muse、hermes 等）。技能不含任何 agent 专属环境变量或产品名。
- **来源说明**：本技能是对开源项目 [Fokkyp/SoftwareCopyright-Skill](https://github.com/Fokkyp/SoftwareCopyright-Skill)（MIT）做功能层面 clean-room 分析后重新实现的版本，修复了原实现的已知缺陷（接口返回结果丢失、章节编号错乱、正文盲替换、自检记录失真、序列图渲染调用错误、演示项目残留等）。
- **许可**：MIT。生成材料是否符合项目实际与版权保护中心官网当前要求，由使用者自行核对；本技能不提供任何法律担保。

## 二、核心设计原则

1. **真实代码，禁止编造**：代码材料只能来自真实项目源码，按完整文件抽取；禁止 AI 编造代码。行业判断、功能取舍、文档正文一律由模型阅读项目后撰写。
2. **零改写正文**：操作手册段落由模型亲写并**原文引用**，脚本不做同义词替换、句式生成或填充扩写。
3. **诚实门禁**：七个阶段全部要求用户显式确认；每道门禁记录内容指纹（SHA-256），已确认的草稿在确认后被修改，对应门禁立即失效，必须重新确认。禁止"用户未选择则默认继续"。
4. **诚实降级**：没有 OfficeCLI 时只推进 Markdown/TXT 草稿，**不伪造成 DOCX**；没有 graphviz 时图纸降级为中文文本框线图，不伪造 PNG。
5. **脚本与模型分工明确**：脚本只负责收集证据、校验结构、执行门禁和编排命令；业务理解与文档内容由模型撰写。
6. **输出位置固定**：所有输出写入当前工作目录下的 `软著/`；正式 Word/TXT 只写入 `软著/申请资料/`，不写临时目录。

## 三、双文档类型

技能在业务理解阶段由模型判定（并经用户确认）软件类型，决定生成哪类文档：

| 类型 | 判定条件 | 产出文档 | 特殊要求 |
| --- | --- | --- | --- |
| `operation` | 有用户可见页面或图形界面（Web、桌面、移动端） | 操作手册 | 需要截图阶段；每模块至少两段模型亲写段落（每段 ≥80 非空白字符） |
| `design` | 无界面软件（嵌入式固件、驱动、库、后端服务、命令行工具） | 技术方案文档 | 模块表与接口表必须能回溯源码；可声明图纸（DOT 源或宿主架构图技能产图）；不得出现页面、按钮等界面词汇 |

判定错误可以改回另一种类型并重新生成。无界面软件的申请表"软件分类"通常选"嵌入式软件"，以用户确认为准。

## 四、完整工作流程

```text
环境探测 → 定位项目 → 项目分析 → 业务理解（模型撰写+用户确认）
→ 代码选择（模型填写+用户确认）→ 代码抽取 → 申请表草稿（用户补全）
→ 图纸渲染（仅 design）→ 文档草稿+自检 → 截图（仅 operation）
→ Markdown 最终确认 → OfficeCLI 生成正式 Word/TXT → 三轮验证
→ 合规审查（软著审查专员，出具审查报告）
→ 第八道门禁：审查确认
```

### 4.1 环境探测（probe_env.py）

启动时先枚举当前 agent 可用的宿主技能与工具（浏览器控制、PDF/DOCX 阅读、视觉理解、联网搜索等），把名称通过 `--host-tools` 传给探测脚本登记，并主动利用它们提升质量：

- **浏览器控制技能**：可作为 `agent-browser` 截图方式，替代 Playwright CLI 安装。
- **PDF / DOCX 阅读技能**：读取无法自动提取正文的证据文档，要点写入业务理解模型稿。
- **视觉能力**：逐张查看渲染后的图纸，确认中文无乱码、无遮挡后再交用户确认。
- **架构图技能（如 archify）**：可为技术方案文档的图纸插槽直接生成图片，落盘到 `软著/图纸原始/` 后由 figures.py 优先采用并登记图纸清单（详见 4.6）。
- **联网搜索**：仅用于行业表达调研，结论写入 `external_research_notes` 并与项目证据区分，不得编造项目不存在的功能。
- **OfficeCLI** 是唯一的 DOCX 写入器；宿主 docx 技能只用于预览与复核，不替代生成。

探测结果输出 `软著/环境探测.{md,json}`，包含 OfficeCLI 路径与版本、graphviz 渲染链、无头浏览器、Playwright CLI、中文字体与宿主工具使用建议。OfficeCLI 缺失、待重启或版本不满足要求（不低于 `1.0.151` 且主版本为 `1`）时会打印 STOP_FOR_USER，由用户选择：全局安装（安装后须重启 coding agent 再重新探测）、切换版本，或明确承担风险（正式生成时传 `--allow-untested-officecli`）。

`scripts/setup_officecli.py` 是安装自检与安装入口：不带参数只做只读检查；`--install` 仅在用户明确同意后执行官方安装器。

### 4.2 定位项目与分析（analyze_project.py）

扫描当前目录找项目根（避开本 skill、`软著/`、node_modules、构建产物、隐藏目录）；**多个候选时停止让用户选择**并记录 `project` 门禁。

分析产出框架、语言、源码文件数与总行数、入口/页面/接口分类、路由与运行命令候选，写入 `软著/analysis/project.json`。

### 4.3 业务理解（business_context.py）

脚本先收集证据（README、docs 下的 PRD/BRD/架构文档、DOCX/ODT 自动提取正文、PDF 在有 pypdf 时提取）并生成模型稿模板；行业、功能、结构判断一律由模型阅读证据后作出。模型撰写模型稿 JSON 的内容包括：

- `manual_kind`（operation/design）、行业、目标用户、核心价值、业务功能与说明、典型流程；
- 申请口径：开发目的 ≤50 字、行业 ≤50 字、主要功能 500~1300 个非空白字符、技术特点 ≤100 字；
- operation 模式的 `manual_modules`（每页至少两段亲写段落）或 design 模式的 `design_spec`（模块、功能、接口、出错处理、可选 DOT 图纸）。

生成 `业务理解.md/json` 后**停止等待用户确认**（含文档类型），确认后记录 `business` 门禁。

### 4.4 代码选择（code_selection.py）与抽取（extract_code.py）

依据《计算机软件著作权登记办法》第十条：程序和文档的鉴别材料一般由**前、后各连续 30 页**组成；不足 60 页时提交全部；程序每页不少于 50 行。

- **候选发现按内容而非扩展名白名单**：可读、大小合理、非文档/配置/二进制/生成物的文本文件全部进入候选，未知扩展名同样进入。
- 脚本只生成候选清单（按入口、路由、页面、数据交互、状态、组件、通用能力、服务端排序），**不默认选择任何文件**；模型阅读后填写 `selected` 与 `model_reason`（优先入口、页面、核心组件、数据交互；不足 60 页再补后端等源码），交用户确认后记录 `code-selection` 门禁。
- 抽取规则：按**完整文件**抽取（不支持只取中间行段）；移除注释与空行（字符串字面量中的注释符号与 C 预处理指令保留）；制表符 4 空格展开后按最多 90 显示列确定性折行（全角按 2 列）；每页按 55 物理行估算选材量；不插入人工分页符，最终分页由 Word 排版引擎完成。
- 已选不足 60 页且候选有富余时脚本停止要求补充；候选全部用尽仍不足则生成全部代码材料。
- 产出 `代码.md`（前30+后30 合并或全部）与 `代码提取清单.{md,json}`（记录文件来源、行数与材料行范围，供追溯；代码正文内不插入文件路径标记）。

### 4.5 申请表信息（application_info.py）

按官网实际表单顺序登记 25 个字段（软件全称、简称、版本号、软件分类、开发完成日期、开发方式、软件说明、发表状态、首次发表日期、著作权人、权利范围、权利取得方式、开发的硬件环境、运行的硬件环境、开发该软件的操作系统、开发环境/开发工具、运行平台/操作系统、运行支撑环境/支持软件、编程语言、源程序量、开发目的、面向领域/行业、主要功能、技术特点、页数）。

用户补全关键字段后记录 `application-fields` 门禁，脚本校验枚举值、日期格式、长度上限与主要功能 500~1300 字窗口。

### 4.6 图纸渲染（figures.py，仅 design 模式）

DOT 图纸自动注入版式默认值（nodesep=0.5、ranksep=0.8、CJK 字体、白底）后渲染为 PNG：

- 中文字体自动探测：Windows 微软雅黑、macOS 苹方、Linux 经 fc-list 探测，避免中文渲染成方框。
- 渲染链优先 `dot -Tpng`（150 DPI），退化为 `dot -Tsvg` 加 cairosvg/inkscape/librsvg/magick；全部不可用时自动输出**中文文本框线图**（分层方框 + 连接关系），纯 UTF-8 中文加制表符，任何环境不乱码、不遮挡；安装 graphviz 后重跑即可升级为 PNG。
- 渲染前 lint：标签单行超过 24 字为阻断级（不渲染 PNG、降级文本图并提示拆行）；连线超 12 条、边标签超 4 处为提示级。
- **宿主架构图技能产图（如 archify）**：模型用宿主架构图技能为已声明插槽生成图片，落盘到 `软著/图纸原始/`，文件名 `数字前缀-插槽名.图片扩展名`（如 `01-architecture.png`，插槽名只能是 architecture/key_N/function_N，支持 png/jpg/jpeg/webp）；figures.py 会**优先采用**宿主图片、跳过该插槽的 DOT 渲染，复制到 `草稿/图纸/` 并在图纸清单登记（backend 为 `host-image`，记录来源）。未匹配已声明插槽、文件名不含插槽名或空文件会被提示且不采用；删除 `图纸原始/` 对应文件重跑即可恢复 DOT 渲染。图纸内容必须对应真实模块结构，生成后须视觉复核；图纸清单与登记图片纳入最终确认指纹，确认后替换图片会使门禁失效。

### 4.7 文档草稿与自检（manual_draft.py）

按对应骨架生成 Markdown 草稿。**操作手册**骨架为：相关文档、说明、功能特点、系统要求、每个真实页面/核心流程独立成章、典型使用流程、常见问题解答、术语表；一级章节标题使用中文大写序号（一、二、三）。**技术方案文档**骨架为：引言、软件总体设计（需求概括/概述/条件与限制/总体结构和模块接口设计/模块功能逻辑关系/设计和描述）、软件功能描述、接口设计（含 API 接口与出错处理设计）；小节编号动态生成不跳号，每个接口必须输出"返回结果"小节。

自检为真实的多轮记录：存在阻断问题时脚本退出，模型修正业务理解或模型稿后重跑，每一轮自检真实追加到自检记录（含正文摘要，可核对每轮内容确实不同），问题清零前不能进入正式生成。自检还会把疑似技术词与空泛套话（旨在、赋能、一站式、高效便捷、显著提升等）列为提示项。

### 4.8 截图（shots.py，仅 operation 模式）

用户必须在四种方式中**显式选择**一种并记录 `screenshot-method` 门禁（脚本不从备注猜测，必须显式传 `--method`）：

1. `agent-browser`：用宿主自带的浏览器控制技能操作真实页面截图，无需额外安装；
2. `playwright-cli`：全局安装的 `@playwright/cli@0.1.20`（探测 PATH 与 `npm prefix -g`，安装后无需重启 agent）；
3. `user-supplied`：用户自行截图放入 `软著/用户截图/`，文件名加数字前缀；
4. `skip`：明确跳过，操作手册保留可见的 `【截图预留：……】` 文字占位，不阻塞正式生成。

截图要求：按模块顺序数字前缀编号（`01-首页.png`）；截取实际视口不留加载动画/调试面板；**不得通过改 DOM、伪造接口响应或注入数据制造不存在的功能**；每张必须落盘且非空；完成后运行 shots.py 生成 `截图清单.json`（status 必须为 ok）。

### 4.9 正式生成（build_final.py）

软件名与版本以 `申请表信息.md` 为准，输出到 `软著/申请资料/`：

- `申请表信息.txt`、`<软件全称>-代码.docx`、`<软件全称>_操作手册.docx` 或 `<软件全称>_技术方案文档.docx`、`生成报告.md`。
- 写入策略：每个 DOCX 先 `create --force --locale zh-CN`，再用一个原子 `batch --stop-on-error` 写入；A4 页面、页边距（代码 1.8cm、文档 2.5cm）、页眉（左：软件全称 版本号；右：第 X 页）全部由命令写入；代码每行一个固定 13pt 行距段落（Consolas 8pt）不设分页符；文档先以 Markdown 元素导入再统一正文格式（宋体 10.5pt、1.5 倍行距、两端对齐、首行缩进 2 字符、标题黑体）。
- 生成后三轮验证：① 文件存在且非空、OpenXML 结构错误必须为 0；② 抽样代码可回溯源码、行业/功能/流程可回溯业务理解；③ 名称版本页数一致，**前30+后30 模式实际页数必须正好 60**（Windows + Word 环境经 `view stats --page-count` 读取真实页数），全部代码模式下实际页数回写申请表 TXT。
- 手册/技术方案文档同样读取真实页数并执行**文档鉴别材料规则**（前30+后30、不足 60 页提交全部、每页不少于 30 行）：超过 60 页时给出超页警告，需压缩内容或按前 30 页 + 后 30 页截取后提交。
- 主题字体六个槽位统一为 Times New Roman / SimSun，避免 WPS 因 Calibri、等线提示缺字体。

### 4.10 合规审查（review_final.py，软著审查专员）

正式生成完成后对 `申请资料/` 全部产物做登记合规复核，结论供用户提交前决策，审查结论随后经第八道门禁确认（见 4.11）：

```bash
<PYTHON> "<SKILL_DIR>/scripts/review_final.py" --workdir 软著
```

分两步。第一步脚本机械核查，产出 `软著/审查/合规审查底稿.{md,json}`，问题分**阻断**（不符合登记口径、提交前必须整改）与**提示**（不影响受理、建议处理）两级并附依据：

- 正式文件存在且非空（申请表 TXT、代码 DOCX、文档 DOCX、生成报告）；
- 申请表字段口径（枚举/日期/长度/500~1300 字/页数与材料一致/开发目的不能只写软件名称）；
- 代码鉴别材料：前30+后30 模式必须 60 页、每页不少于 50 行（材料末页不足为提示级）、无空行残留（《计算机软件著作权登记办法》第十条）；
- 代码真实性：项目源码可访问时逐行回溯，提交材料每一行都必须能在清单登记的源码中找到（非抽样，编造代码必然暴露）；
- 名称版本一致性：交付文件名、代码清单、文档标题与申请表全称统一；
- 文档骨架复用自检逻辑；截图方式与清单一致、图片落盘非空；图纸清单全部 ok/text；
- 上游七道门禁指纹仍有效（确认后草稿被改动即阻断）；生成报告警告逐条列为提示。

底稿结论：有阻断→不通过；仅提示→整改后通过；无问题→通过。第二步模型以软著审查专员身份阅读底稿与正式文件（有宿主 docx/视觉技能时抽查 DOCX 页眉、标题、截图与图纸乱码），撰写 `软著/审查/审查报告.md`：审查结论（与底稿一致，**脚本阻断项不得降级或省略**）、逐项合规情况（对应底稿 R 编号）、问题与整改建议（指明回到哪个阶段重跑）、提交前检查清单。整改一律回到对应阶段重新生成并重新确认，不得直接改正式文件；审查报告不写入 `申请资料/`。

### 4.11 第八道门禁：审查确认（confirm_gate.py --stage review）

```bash
<PYTHON> "<SKILL_DIR>/scripts/confirm_gate.py" --workdir 软著 --stage review --note "<用户确认内容>"
```

审查报告出具后由用户确认审查结论，记录门禁到 `软著/审查/合规审查确认.json`。

**与前七道的语义差别**：前七道确认的是过程产物（草稿、字段、截图方式）；本道确认的是**最终交付物的可提交性**，因此指纹覆盖 `申请资料/` 全部正式文件与 `审查/审查报告.md`。正式材料在审查确认后被改动，门禁立即失效，审查脚本会把该情况列为阻断项，必须重新审查再确认。

确认前的校验：

1. 上游七道门禁仍全部有效（`build_final.confirmation_issues`）；
2. `审查/审查报告.md` 存在且非空；
3. 报告在「审查结论」处明确写出结论（通过 / 整改后通过 / 不通过）——不认模板占位或正文措辞；
4. 结论不得为「不通过」：存在阻断项时，整改前不允许确认。

## 五、八道门禁一览

| # | 门禁（--stage） | 确认内容 | 失效条件 |
| --- | --- | --- | --- |
| 1 | `environment` | OfficeCLI 处置方式（安装/切换版本/承担风险） | — |
| 2 | `project` | 候选项目目录的选择 | — |
| 3 | `business` | 用途、行业、用户、核心功能与文档类型 | 业务理解.json 被修改 |
| 4 | `code-selection` | 模型填写的代码选择（须含 model_reason） | 代码文件选择.json 被修改 |
| 5 | `screenshot-method`（仅 operation） | 四种截图方式显式四选一（必须传 --method） | 记录被修改 |
| 6 | `application-fields` | 申请表全部关键字段 | 申请表信息.md 被修改 |
| 7 | `markdown` | Markdown 草稿整体确认 | 校验全部上游门禁指纹 + 草稿完整性 + 自检清零；任何已确认文件被改过都会被拦下 |
| 8 | `review` | 合规审查报告的审查结论（通过 / 整改后通过） | 申请资料/ 下正式文件或 审查/审查报告.md 被修改 |

第八道门禁与前七道语义不同：前七道确认**过程产物**（草稿、字段、截图方式），第八道确认**最终交付物的可提交性**，因此指纹覆盖 `申请资料/` 与 `审查/审查报告.md`；正式材料在审查确认后被改动即失效，必须重新审查再确认。确认前校验：上游七道门禁仍有效、审查报告存在、结论在「审查结论」处明确写出、结论不得为「不通过」（存在阻断项时整改前不允许确认）。

需要用户停止等待的时机：OfficeCLI 异常、多个候选项目、业务理解草稿、登记字段、代码候选清单、截图方式、Markdown 草稿整体确认、审查报告出具后确认审查结论。脚本以 `STOP_FOR_USER` + `NEXT_ACTION` 输出提示。

## 七、安装与运行要求

- **安装**：把包含 SKILL.md 的目录整体复制到所用 agent 的 skill 目录（如 zcode 的 `~/.zcode/skills/`、通用 `~/.agents/skills/`、或项目级目录；部分 agent 需在配置中登记路径后重启会话）。`tests/` 可以不复制。
- **Python 3.10+**，脚本均为纯标准库 CLI，Windows/macOS/Linux 通用；脚本输出为 UTF-8 中文，Windows 控制台异常时可重定向到文件查看。
- **OfficeCLI**（正式 Word 的唯一后端；版本要求：不低于 `1.0.151` 且主版本为 `1`，官方安装器的最新版通常即满足）：
  - Windows PowerShell：`irm https://raw.githubusercontent.com/iOfficeAI/OfficeCLI/main/install.ps1 | iex`
  - macOS/Linux：`curl -fsSL https://raw.githubusercontent.com/iOfficeAI/OfficeCLI/main/install.sh | bash`
  - 必须全局安装，安装后重启 coding agent 刷新 PATH；不使用项目内便携版或 `OFFICECLI_PATH` 覆盖。
- **可选增强**：graphviz（DOT 渲染 PNG）、Node 18+ 与 `@playwright/cli@0.1.20`（仅 playwright-cli 截图方式）、pypdf（PDF 证据正文提取）。宿主自带架构图技能（如 archify）无需额外安装，图片放入 `软著/图纸原始/` 即被 figures.py 优先采用。
- **使用**：在打开目标项目的 agent 会话中说 `使用 softcopy-materials 为当前项目生成软著材料`，按流程引导逐步确认；完整命令示例见 [使用示例.md](使用示例.md)。

## 八、使用注意事项

### 必须遵守的规则

1. **门禁不可跳过**：涉及用户选择或确认的阶段必须停止等待输入，禁止"未选择则默认继续"；草稿在确认后被修改，对应门禁自动失效，须重新确认后才能正式生成。
2. **按阶段阅读参考文档**，不要一次全部加载：填申请表前读 `fields.md`、研判业务前读 `business.md`、选择抽取代码前读 `code-material.md`、写操作手册前读 `manual.md`、写技术方案文档前读 `design.md` 与 `figures.md`、截图前读 `shots.md`、正式生成前读 `docx.md`。
3. **命令中的尖括号是必须替换的占位符**：`<SKILL_DIR>`（SKILL.md 所在绝对目录）、`<PYTHON>`（Python 3.10+ 解释器）、`<项目目录>`、`<软件全称>`、`<版本号>`、`<用户选择>` 等。
4. **不得编造**：不得把测试项目或范本的名称、流程、文案写成通用内容；不得编造项目不存在的功能、模块或接口；外部调研只用于理解行业表达并与项目证据区分。

### 字段填写口径

- **软件全称、版本号、著作权人、日期类字段必须由用户确认**，脚本给出的值只是建议；全称建议以「软件」「平台」「系统」结尾，一旦确认，正式文件名、页眉、标题与正文全部以此为准。
- 项目版本低于 V1.0 时会提醒：软著首次提交通常建议 V1.0，由用户决定。
- **开发环境/开发工具只填 IDE**（如 Visual Studio Code、WebStorm），禁止填 React、Vite、TypeScript 等技术栈。
- 源程序量按分析得到的全部源码总行数（含空行）给出建议值，与已抽取材料行数无关；页数在前30+后30 模式下为 60，由正式生成按 Word 实际分页回写修正。
- 各环境字段、开发目的、行业 ≤50 字符，技术特点 ≤100 字符，编程语言 ≤120 字符，主要功能 500~1300 个非空白字符（不满足直接拒绝，脚本不扩写）。

### 已知局限与降级

- **正则字面量误判**：正则字面量中的 `//`（如 `const re = /\/\//`）会被误判为行注释而截断该行，正则密集的文件建议人工复核。
- 无 OfficeCLI 时只推进 Markdown/TXT 草稿，不伪造 DOCX；OfficeCLI 版本不匹配时须用户明确承担风险（`--allow-untested-officecli`）才能正式生成。
- 无 graphviz 时图纸降级为中文文本框线图（不是 PNG），或改用宿主架构图技能（如 archify）经 `图纸原始/` 产图；标签单行超过 24 字会被 lint 阻断 PNG 渲染并提示拆行。
- 预览截图可选生成，**HTML 渲染不能替代 Word/WPS 最终复核**。

### 提交前

把需要上传的 docx 另存为 PDF，按中国版权保护中心官网要求填报；生成材料是否符合项目实际与官网当前要求由使用者自行核对。
