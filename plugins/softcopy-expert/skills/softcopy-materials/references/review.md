# 合规审查规则（软著审查专员）

正式生成（build_final）完成后，对 `申请资料/` 全部产物做登记合规复核：脚本先做机械核查并产出底稿，模型再以软著审查专员身份出具审查报告，随后由用户确认审查结论（第八道门禁）。

## 脚本侧机械核查（review_final.py）

```bash
<PYTHON> "<SKILL_DIR>/scripts/review_final.py" --workdir 软著
```

产出 `软著/审查/合规审查底稿.{md,json}`，核查项：

1. 正式文件存在且非空：申请表信息.txt、`<软件全称>-代码.docx`、`<软件全称>_操作手册.docx` 或 `_技术方案文档.docx`、生成报告.md。
2. 申请表字段口径：枚举、日期格式、长度上限、主要功能 500~1300 字、页数为正整数且与代码材料实际页数一致；开发目的不能只写软件名称。
3. 代码鉴别材料：前30+后30 模式必须 60 页；每页不少于 50 行（材料末页不足记提示级）；正文不得残留空行。依据《计算机软件著作权登记办法》第十条。
4. 代码真实性：项目源码可访问时**逐行回溯**——提交材料每一行都必须能在代码提取清单登记的源码文件中找到，任何一行编造代码都会被抓出（非抽样）。
5. 名称版本一致性：交付 docx 文件名、代码提取清单的软件名/版本号、说明文档标题与申请表全称统一。
6. 文档骨架：复用文档自检逻辑（必备章节齐全、design 模式不得出现界面词汇、无制式字段标题、正文无列表行、无占位残留）。
7. 截图合规（operation）：方式已确认且与清单一致、清单状态 ok、每张图片落盘非空、数量与手册预留位置匹配；skip 是合法选择，记录备注不作为问题。
8. 图纸合规（design）：图纸清单全部 ok/text；文本框线图记提示（可安装 graphviz 或用宿主架构图技能产图升级 PNG）。
9. 门禁链：七道门禁指纹仍全部有效——确认后草稿被改动即阻断，因为正式资料必须与用户确认过的草稿一致。
10. 生成报告中的警告逐条列为提示。

分级：**阻断**=不符合登记口径、提交前必须整改；**提示**=不影响受理、建议处理。
底稿结论：有阻断→不通过；仅提示→整改后通过；无问题→通过。

## 模型侧审查专员职责

- 阅读底稿全部问题与证据摘要；阅读正式文件正文草稿与生成报告；具备宿主 docx/视觉技能时抽查正式 DOCX：页眉名称与版本、标题、截图与图纸是否乱码遮挡、整体排版。
- 撰写 `软著/审查/审查报告.md`，结构：
  1. **审查结论**：通过 / 整改后通过 / 不通过，与底稿一致；脚本阻断项不得降级、不得省略。
  2. **逐项合规情况**：对应底稿编号（R01…）逐条说明合规与否。
  3. **问题与整改建议**：每个阻断项指明回到哪个阶段重跑（如申请表字段→补全后重记 application-fields 门禁；代码页数→回到代码选择重新校准选材量）。
  4. **提交前检查清单**：docx 在 Word/WPS 复核后另存 PDF、按中国版权保护中心官网当前要求填报、材料真实性由使用者负责。
- 禁止为"通过审查"建议直接修改正式文件或绕过门禁；一切整改回到对应阶段重新生成并重新确认。审查报告不写入 `申请资料/`（它不是提交材料）。

## 第八道门禁：审查确认

审查报告出具后由用户确认结论：

```bash
<PYTHON> "<SKILL_DIR>/scripts/confirm_gate.py" --workdir 软著 --stage review --note "<用户确认内容>"
```

记录位置：`软著/审查/合规审查确认.json`。

与前七道的语义差别：前七道确认**过程产物**，本道确认**最终交付物的可提交性**，因此指纹覆盖 `申请资料/` 全部正式文件与 `审查/审查报告.md`。正式材料在审查确认后被改动，门禁立即失效，审查脚本会把它列为阻断项。

确认前的校验：

1. 上游七道门禁仍全部有效；
2. `审查/审查报告.md` 存在且非空；
3. 报告在「审查结论」处明确写出结论（通过 / 整改后通过 / 不通过）——不认模板占位、不从正文措辞猜测；
4. 结论不得为「不通过」：存在阻断项时，整改前不允许确认。

## 审查结论的写法

报告必须有一处明确的结论声明，脚本据此判定：

```markdown
## 一、审查结论

通过
```

或行内写法 `审查结论：整改后通过`。

结论只能取三个值之一，且必须与底稿一致——脚本阻断项不得降级、不得省略。模板里的「通过 / 整改后通过 / 不通过」并列不算结论。
